# Contributing

Thanks for helping. Bug reports with a small export that shows the problem are the most
useful contribution of all; please make up the content (see [Test data](#test-data)).

## Setup

You need Node.js 22.12 or newer (24 for the integration tests is fine too).

```bash
npm ci
npm ci --prefix test/payload-project
```

The second command installs the small Payload 3 project the integration tests run in. It is
big (Payload brings Next.js), and only needed for `npm run test:integration`.

## Checks

```bash
npm run lint          # ESLint and Prettier
npm run typecheck
npm test              # unit tests, fast, no Payload needed
npm run build
npm run test:integration   # temporary Payload projects on SQLite; needs the build
npm run test:external      # WordPress Theme Unit Test data, downloaded at run time
```

Run lint, typecheck and the unit tests before every push; CI runs all of them and the
integration tests on Node 22 and 24. `npm run format` fixes formatting.

## Project layout

```
src/
  wxr/        streaming WXR reader and the first-pass index
  analyze/    the analyze command's detectors, rating and reports
  content/    blocks, autop, shortcodes and the HTML clean-up before Lexical
  paths/      URL patterns and old-to-new URL mapping
  redirects/  redirect map and its six formats
  seo/        Yoast and Rank Math
  scaffold/   collection templates
  import/     the import: runner (inside `payload run`), schema checks, media, Lexical
  commands/   one file per CLI command
test/
  unit/        unit tests
  integration/ end-to-end tests against real Payload projects
  external/    Theme Unit Test data
  fixtures/    synthetic WXR files
  golden/      expected output of the redirect formats
```

## Test data

- Fixtures are **synthetic**: made-up names, `example.com`-style domains, texts written for
  the test. Never commit a real export, a client's content, real e-mail addresses, or files
  from a real site.
- No code, test data or fixtures under the GPL. In particular, do not copy code from
  WordPress (its block parser, `wpautop`, shortcode parsing) or files from the Theme Unit Test
  data. Implement behaviour from its description instead.
- Binary test files are generated by the tests (see `test/support/png.ts`).
- Golden files are updated with `UPDATE_GOLDEN=1 npm test`; review the diff.

## Changes

- Small, focused pull requests with tests. Conventional commit messages (`feat:`, `fix:`,
  `docs:`, …) in English.
- New warning codes go into `src/report/warnings.ts` and [docs/warnings.md](docs/warnings.md).
- Behaviour visible to users goes into [CHANGELOG.md](CHANGELOG.md) under "Unreleased".
- Keep runtime dependencies to a minimum; discuss a new one in an issue first.
- `main` only changes through pull requests with green CI.

## Releasing

Releases are published to npm by [`.github/workflows/publish.yml`](.github/workflows/publish.yml)
when a version tag is pushed. It uses npm trusted publishing: npm trusts the workflow through
GitHub's OIDC token, so there is no npm token in the repository, and every release gets a
provenance attestation. The first version, 0.1.0, is published by hand; trusted publishing is
configured in the package's settings on npmjs.com.

1. On a branch, prepare the release:

   ```bash
   npm version 0.2.0 --no-git-tag-version
   ```

   This updates `package.json` and `package-lock.json`. In [CHANGELOG.md](CHANGELOG.md), turn
   the unreleased section into `## [0.2.0] - YYYY-MM-DD`. Commit as `chore: release 0.2.0`,
   open a pull request to `main` and merge it once CI is green.

2. Tag the merge commit on `main` and push the tag:

   ```bash
   git switch main && git pull
   git tag -a v0.2.0 -m "wp-to-payload 0.2.0"
   git push origin v0.2.0
   ```

3. The workflow checks that Node.js is 22.14 or newer and npm 11.5.1 or newer, that the tag
   matches the version in `package.json` and that the tagged commit is on `main`. It then runs
   lint, typecheck, unit tests and the build, and publishes. Versions with a pre-release part
   (`0.3.0-beta.1`) are published under the `next` dist-tag, all others under `latest`.

4. Create a GitHub release from the tag with the changelog entry.

A tag for a version that is already on npm (for example `v0.1.0`, published by hand) ends the
workflow without publishing, so such tags can be added for the history.

If the workflow fails before publishing, fix the problem on `main` through a pull request,
delete the tag (`git push origin :refs/tags/v0.2.0` and `git tag -d v0.2.0`) and tag again.
A version that reached npm cannot be published again; release the next patch version instead.
